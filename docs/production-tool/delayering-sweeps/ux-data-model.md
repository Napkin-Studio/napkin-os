## Short answer

Every mature editor, open or closed, has converged on the same core: a **flat or shallow tree of layer records**, each with its own pixel asset, a transform, a visibility/opacity/blend triple and an optional mask, plus **per-layer non-destructive effects** (GIMP 3.x "Fx", Krita filter and transform masks, Photoshop adjustment and generative layers). Ordering is a per-sibling sort key, and the collaborative tools (Figma, tldraw, Excalidraw, Loro, the Yjs community pattern) all use a **fractional index string with a tie-break on the record id**, with records keyed by id so that moves and reorders are single-field writes. The open interchange format that matches this model one-to-one is **OpenRaster (ORA)**: a zip of per-layer PNGs, a `stack.xml` with `x, y, opacity, visibility, composite-op`, nested stacks for groups, and a mandatory `mergedimage.png` composite. PSD write is available under MIT via **ag-psd**, with the caveat that we must render the composite ourselves.

The 2025-2026 AI products present auto-made layers as exactly this kind of record: Seedream 5.0 Pro Layerize returns a base image plus up to 16 transparent PNGs each with `z_index`, a bounding box, a name and a description; Qwen-Image-Layered (Apache 2.0) returns a variable number of full-canvas RGBA layers ordered bottom to top and ships a PSD/PPTX exporter; Canva Magic Layers turns a flat PNG/JPG into separately movable elements with text restored as live text; Adobe's Layered Image Editing was still "in development" at MAX 2025 and no primary source confirms it shipped since. Per-layer provenance has a standard home: C2PA 2.2 ingredients with `componentOf` and a `c2pa.placed` action, with `regionOfInterest` rectangles in pixels and `compositeWithTrainedAlgorithmicMedia` as the digital source type.

Recommendation: model (i), a **layer entity list per frame version** with records keyed by id, a fractional `rank`, a nullable `parentId` reserved for groups, a per-layer `effects` list for non-destructive adjustments, a layer-level `source` block that maps to C2PA, and a content-addressed cached composite. Treat the existing edit list as the history of operations on those records, not as the model (option ii), and keep a separate layered document (option iii) only as a later refactor if layered images start being reused across frames.

## Findings

### 1. Layered raster formats and permissively licensed libraries

**OpenRaster (ORA), spec 0.0.6, draft.** Primary: https://www.openraster.org/baseline/file-layout-spec.html and https://www.openraster.org/baseline/layer-stack-spec.html (page footer ©2018; fetched 2026-10-23). A zip whose first entry is an uncompressed `mimetype` containing `image/openraster`; a UTF-8 `stack.xml`; layer PNGs under `data/` referenced by full path; `mergedimage.png` **mandatory since 0.0.2**, PNG at 8 or 16 bits per channel, "the final rendered image"; `Thumbnails/thumbnail.png` mandatory, non-interlaced 8-bit, at most 256x256. `stack.xml`: `image` carries `w`, `h`, `version` and optional `xres`/`yres`; `layer` has required `src` and optional `name`, `x`, `y` (signed ints), `opacity` 0.0-1.0, `visibility` visible|hidden, `composite-op`; `stack` elements nest ("may contain sub-stacks, layers, or text elements") and carry `name`, `opacity`, `visibility`, `composite-op`, `isolation` (isolate|auto); `x`/`y` on stacks were removed in 0.0.6. Composite ops are the SVG set: `svg:src-over` (default), multiply, screen, overlay, darken, lighten, color-dodge, color-burn, hard-light, soft-light, difference, color, luminosity, hue, saturation, plus, dst-in, dst-out, src-atop, dst-atop. Wikipedia lists the spec as "draft" and "supported by a few programs" (secondary, https://en.wikipedia.org/wiki/OpenRaster).

**GIMP's ORA plug-in shows what real writers do.** Primary: https://gitlab.gnome.org/GNOME/gimp/-/raw/master/plug-ins/python/file-openraster.py (master, fetched 2026-10-23). It reads and writes `src, name, x, y, opacity, visibility, composite-op` plus the non-spec attributes `selected` and `edit-locked`; nested stacks become group layers; it never reads `mergedimage.png` on load and regenerates it (flatten of visible layers) on save; it writes layer PNGs at 100% opacity because opacity lives in `stack.xml`; it does not handle masks or layer effects; GIMP blend modes with no SVG equivalent are written as `svg:src-over`. Krita's docs describe ORA as "designed to replace *.psd as an interchange format", layers "as *.png" (primary: https://docs.krita.org/en/general_concepts/file_formats/file_ora.html).

**PSD, via ag-psd (MIT).** Primary: https://github.com/Agamnentzar/ag-psd and https://raw.githubusercontent.com/Agamnentzar/ag-psd/master/LICENSE ("The MIT License (MIT)", copyright Agamnentzar 2016); version 31.0.3 per https://cdn.jsdelivr.net/npm/ag-psd/package.json with runtime deps `base64-js` and `pako` only (fetched 2026-10-23). `readPsd`/`writePsd`; nested layer tree via `children`; layer masks; smart-object (`placedLayer`) metadata and linked files; text read/write "incomplete"; effects limited. Limits that matter to us: RGB only for writing, no 16-bit, no PSB, and "the library does not regenerate the composite image when layers, blending or pixel data change": we must set `psd.canvas` or `psd.imageData` ourselves, or leave the composite out (Photoshop opens without it). Node needs `node-canvas` or `useImageData`; web workers need `OffscreenCanvas`.

**PSD readers for the browser.** `@webtoon/psd` (MIT, NAVER WEBTOON; primary https://github.com/webtoon/psd): read-only, WebAssembly decode, PSB support, groups as a tree, `composite()` per layer or whole image, about 100 KiB; whole-image `composite()` returns nothing unless the file was saved with "Maximize Compatibility". `psd.js` (MIT; primary https://github.com/meltingice/psd.js): read-only, CoffeeScript, PNG export uses Photoshop's saved preview so it is empty without compatibility mode; 172 open issues, documentation "work in progress". Python: `psd-tools` (MIT; primary https://github.com/psd-tools/psd-tools) reads and writes the low-level structure, can add/remove pixel layers and groups, composites basic pixel layers, limited adjustment layers, no font rendering.

**PSD layer records, for mapping.** Primary: Adobe Photoshop File Formats Specification, November 2019, https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/. Each layer record has a bounding rectangle, channel list, blend mode key, opacity, clipping, flags, mask data and name; groups are `lsct` section dividers (1 open, 2 closed, 3 bounding divider); `luni` is the Unicode name, `lyid` a layer id, `SoLd` the placed (smart object) layer descriptor (CS3+).

**Layered TIFF is PSD layer data in a TIFF tag.** Same Adobe spec: tag 37724 `ImageSourceData` starts with "Adobe Photoshop Document Data Block" and tag 34377 holds the image resources; details live in the separate "Photoshop TIFF Technical Notes" (2002). The Python library `psdtags` (BSD-3-Clause, v2026.1.29; primary https://pypi.org/project/psdtags/) reads and writes both tags. Conclusion: layered TIFF is not a simpler target than PSD; it is PSD with a TIFF wrapper.

**Krita .kra.** Primary: https://docs.krita.org/en/general_concepts/file_formats/file_kra.html: a zip "vaguely based on the open document standard" with `mergedimage.png` always RGBA (or grayscale), read as a fallback by Scribus; `.krz` is the same without the merged image. Per-layer pixels are Krita's own tile format: 64x64 tiles, per-tile LZF or NONE compression, header `VERSION 2 / TILEWIDTH / TILEHEIGHT / PIXELSIZE / TILESNUMBER` (primary but old: https://community.kde.org/Krita/Tile_Data_Format, last edited 2010-07-07). Not a candidate for interchange.

**Photopea is not a library.** Primary: https://www.photopea.com/api/accounts (fetched 2026-10-23): embedding in an iframe is free with branding; white-label needs a Distributor account priced by monthly views; self-hosting costs $500-2,000 per month, paid 12 months ahead, two updates a year free and $300 per extra update; no open-source licence is mentioned.

### 2. How open-source editors model layers and non-destructive edits

**GIMP 3.0 (released 2025-03-16).** Primary: https://www.gimp.org/release-notes/gimp-3.0.html and https://www.gimp.org/news/2025/03/16/gimp-3-0-released/. Filters "stay active once committed"; they are re-editable from the layer's Fx menu, can be toggled, selectively deleted or merged down; a "Merge Filters" option restores the 2.10 destructive behaviour; filter stacks save to XCF, and third-party filters are discarded when the plug-in is missing at load. The model is **effects attached to the layer**, not a global operation list.

**GIMP 3.2 (released 2026-03-14).** Primary: https://www.gimp.org/news/2026/03/14/gimp-3-2-released/ and https://www.gimp.org/release-notes/gimp-3.2.html. Filters also apply to channels and to layer groups; an empty group in pass-through mode with a filter acts as an adjustment layer; new Link Layers (external file, auto-updates on change) and Vector Layers; all three non-destructive layer types have **Rasterize / Revert Rasterize**; PSD import gains Drop Shadow, Inner Shadow and Outer Glow styles; PSB export added.

**Krita.** Primary: https://docs.krita.org/en/user_manual/layers_and_masks.html. Non-destructive editing means "changes are just added as filters or masks over the original image while keeping it intact"; filter masks apply filters to one layer, filter layers to everything below, transform masks transform a layer non-destructively, transparency masks hide parts; all can be applied to a group. Layer types listed in the reference manual include Clone, File, Fill, Filter, Group, Paint, Vector (primary: https://docs.krita.org/en/reference_manual/layers_and_masks.html).

**Penpot.** Primary: https://help.penpot.app/technical-guide/developer/data-model/penpot-file-format/ and the live change schema https://raw.githubusercontent.com/penpot/penpot/develop/common/src/app/common/files/changes.cljc (develop, fetched 2026-10-23). A `.penpot` zip stores one JSON per shape under `files/{file}/pages/{page}/{shape}.json`; a shape has `id, name, type, parentId, frameId`, geometry `x, y, width, height, selrect, points`, and `transform`/`transformInverse` matrices; frames, groups and bools carry a `shapes` array of child UUIDs. Order is **position in the parent's `shapes` vector**: the `mov-objects` change takes `parent-id`, `shapes` and an optional integer `index` or `after-shape`, and inserts with `insert-at-index` or appends; `reorder-children` is a separate change type. Penpot is server-sequenced, so integer indexes work for it; they would not merge offline.

**Polotno.** Primary: https://polotno.com/docs/schema/page and https://polotno.com/docs/schema/image-element (fetched 2026-10-23). Store → pages → `children` array of typed elements; an `image` element has `id, name, opacity, visible, selectable, removable, alwaysOnTop, showInExport, x, y, width, height, rotation, blurEnabled, brightness, src, cropX, cropY, cropWidth, cropHeight, cornerRadius, flipX, flipY, clipSrc, borderColor, borderSize, keepRatio, draggable, resizable, contentEditable, styleEditable, custom` and shadow fields. Order is the array (inferred; the schema has no z field). The notable detail is the **split of permission flags** (`selectable, removable, draggable, resizable, contentEditable, styleEditable`) rather than one `locked`.

**Excalidraw.** Primary: PR #7359 "feat: fractional indexing", merged 2024-04-04, https://github.com/excalidraw/excalidraw/pull/7359, and the current https://raw.githubusercontent.com/excalidraw/excalidraw/master/packages/element/src/fractionalIndex.ts. Each element carries `index` generated with the `fractional-indexing` package; invariant: "for every element in the elements array, its fractional index is strictly smaller than the next element's"; the array is kept as a cache of order for backwards compatibility; conflicting indices after reconciliation are ordered by `element.id` and then deduplicated by generating a key between valid neighbours; `syncMovedIndices` touches only moved elements and falls back to `syncInvalidIndices`.

**tldraw.** Primary: https://tldraw.dev/sdk-features/shape-indexing, https://tldraw.dev/sdk-features/parenting, https://tldraw.dev/reference/tlschema/TLBaseShape, https://tldraw.dev/docs/sync. A shape record has `index: IndexKey` (strings like `a1`, `a1V`), `parentId: TLPageId | TLShapeId`, `x, y, rotation`; "shape indices are always relative to siblings within the same parent"; index generation is **jittered** so two users inserting at the same spot "generate different indices instead of identical ones"; the store validates indices on write; `reparentShapes(shapes, parentId, index?)` keeps page positions and recomputes local coordinates; `sendBackward`/`bringForward` only pass shapes whose bounds overlap unless `considerAllShapes` is set; a shape is effectively locked if any ancestor is locked. Sync: `TLSocketRoom` "stores the authoritative copy of the document"; conflict semantics beyond that are not on the public page.

### 4. Per-layer provenance: C2PA 2.2

Primary: C2PA Technical Specification 2.2 (May 2025), https://spec.c2pa.org/specifications/specifications/2.2/specs/C2PA_Specification.html; Implementation Guidance 2.2, https://spec.c2pa.org/specifications/specifications/2.2/guidance/Guidance.html; CAI SDK docs https://opensource.contentauthenticity.org/docs/manifest/writing/ingredients/ and https://opensource.contentauthenticity.org/docs/manifest/writing/assertions-actions/ (all fetched 2026-10-23).

- Ingredient v3 (`c2pa.ingredient.v3`): `dc:title`, `dc:format` (optional), **`relationship` required** with values `parentOf` (the opened original, at most one, paired with `c2pa.opened`), `componentOf` (one of several parts, paired with `c2pa.placed`) and `inputTo` (input to a computational process such as an AI model); `instanceID`, `thumbnail`, `data`, `activeManifest`, `claimSignature`, `validationResults`, `description`, `metadata`. An ingredient's own manifests are inserted into the composed asset's manifest store, so provenance nests.
- Actions v2: `c2pa.created`, `c2pa.opened`, `c2pa.placed` ("Added/Placed one or more componentOf ingredient(s)"), `c2pa.edited`, `c2pa.removed` ("A componentOf ingredient was removed"), `c2pa.cropped`, `c2pa.resized`, `c2pa.color_adjustments`; actions reference ingredients through `parameters.ingredients` (spec) / `parameters.ingredientIds` (SDK); v2 has a **`changes` field: an array of `region-map` objects** describing changed regions.
- Regions: a `region-map` has `description` and `region` entries; a spatial shape in the example is `{type: rectangle, unit: pixel, origin {x, y}, width, height}`; assertion metadata can carry `regionOfInterest` describing "the relevant portions of the ingredient that were used".
- Digital source types: `trainedAlgorithmicMedia` for fully generated media; `compositeWithTrainedAlgorithmicMedia` "a composite that includes trained algorithmic media, such as through inpainting or outpainting"; the guidance (§5.2.2) says a generative fill "could be recorded as a c2pa.edited or c2pa.placed action" with the composited source type.
- Adobe's practice (primary, Adobe learn: https://www.adobe.com/uk/learn/photoshop/web/apply-content-credentials-photoshop): credentials are enabled per document, not per layer; the recorded ingredients include "a Generative Fill layer" and an added photo; credentials are attached to the exported file or published to Adobe's cloud. Community reports that credentials are appended automatically whenever Generative Fill was used (helpx page refused the fetch; **unverified**).

So a per-layer provenance model maps cleanly: each AI-made layer is a `componentOf` ingredient placed with `c2pa.placed`, its transform becomes a pixel rectangle in `changes` or `regionOfInterest`, and the flattened export carries `compositeWithTrainedAlgorithmicMedia`. Neither ORA nor PSD carries a C2PA manifest; it goes on the exported PNG/JPEG/MP4.

### 5. Collaborative editing of ordered layer lists

**Fractional indexing, the shared answer.** Primary: Figma, "Realtime editing of ordered sequences", 2017-03-06, https://www.figma.com/blog/realtime-editing-of-ordered-sequences/: each child has a fraction strictly between 0 and 1 stored as a base-95 string; inserting takes the midpoint; reordering changes only the moved object; two clients inserting at the same spot produce identical indices and "the server prevents this by assigning a unique position to the second insert"; interleaving of concurrent runs is accepted for design documents. Evan Wallace, "CRDT: Fractional Indexing", 2022-11-12, https://madebyevan.com/algos/crdt-fractional-indexing/: sort by position then by object id; use arbitrary-precision strings not floats (64-bit floats exhaust after about 50 halvings); add random jitter so identical keys are improbable; last-writer-wins with peer id tie-break; no tombstones needed. Library: `fractional-indexing` (CC0, base-62, `generateKeyBetween`, `generateNKeysBetween`; primary https://github.com/rocicorp/fractional-indexing), the package Excalidraw uses.

**Figma's tree and reparenting.** Primary: "How Figma's multiplayer technology works", 2019-10-16, https://www.figma.com/blog/how-figmas-multiplayer-technology-works/. The document is `Map<ObjectID, Map<Property, Value>>`; the server keeps the last value per property (LWW per property, not per object); **the parent link and the position are stored as one property so they update together**; concurrent reparents can form a cycle, which the server rejects, and the client temporarily removes the affected objects from the tree until the rejection arrives; undo must not overwrite other people's later edits ("an undo modifies the redo history at that moment").

**Yjs: arrays cannot move.** Primary: Yjs maintainer thread, 2020, https://discuss.yjs.dev/t/moving-elements-in-lists/92. Delete-then-insert "might duplicate content if two users move an element at the same time"; the recommended pattern is a `Y.Array` of `Y.Map` items each holding a position value, sorted on read, moving by setting the position; a top-level `Y.Map` keyed by id works but "deleted properties will always take up space (the key-name can't be removed)"; "re-parenting on maps is currently not supported". The Yjs course lesson on this (learn.yjs.dev) was paywalled (402).

**Loro: native move.** Primary: https://docs.rs/loro/latest/loro/struct.LoroMovableList.html and https://docs.rs/loro/latest/loro/struct.LoroTree.html; MIT per https://github.com/loro-dev/loro. `LoroMovableList` adds `set` and `mov` because emulating them with insert and delete "fails in concurrent editing scenarios"; `LoroTree` has `mov`, `mov_to`, `mov_after`, `mov_before` and `enable_fractional_index(jitter)` for sibling order, with the warning that jitter "will affect the growth rate of document size". The movable-tree blog post was not fetchable (403); the tutorial pages 403 as well.

**Penpot and tldraw are server-ordered.** Penpot applies integer-index `mov-objects` changes in server order (see §2); tldraw's `TLSocketRoom` holds the authoritative copy and jitters its fractional indices anyway. Both show that fractional ranks are cheap insurance even with a server in the loop.

### 6. Image-layer versioning patterns

- **Layer as asset plus transform.** ORA stores each layer as a PNG with `x, y` in `stack.xml` and opacity outside the pixels (GIMP writes layer PNGs at 100% and keeps opacity in XML). Photoshop smart objects (`SoLd`) and GIMP 3.2 Link Layers keep the source asset separate and re-render on change. Seedream returns cropped layers with a bounding box; Qwen returns full-canvas layers with identity placement. A record of `{asset, transform}` covers all four.
- **Baked composite as a cache, not as truth.** ORA's `mergedimage.png` is mandatory and regenerated on save; Krita's `mergedimage.png` exists so other apps can open the file; PSD's composite is optional for Photoshop but required by `psd.js` and `@webtoon/psd` to show anything; ag-psd warns the composite goes stale unless the writer re-renders it. Every format treats the flattened image as a derived artefact that must be kept in step.
- **Variants on the layer.** Photoshop's generative layer keeps all variations and each one adds to the file size; combining two variants means duplicating the layer and masking. A layer record with a `variants[]` list and an `activeVariant` matches this and avoids a layer explosion.
- **Reversible rasterisation.** GIMP 3.2's Rasterize / Revert Rasterize keeps the editable form alongside the raster. For us: never delete the per-layer assets when a user "flattens"; keep the composite as another asset.

**Video handoff constraint.** Primary: https://docs.dev.runwayml.com/assets/inputs/ (fetched 2026-10-23). Runway accepts JPEG, PNG and WebP; URL inputs up to 16 MB, data URIs 5 MB encoded, ephemeral uploads 200 MB; per-model aspect-ratio windows (Gen-4 0.5-2.358, Gen-4.5 0.5-2); the page does not say whether alpha is preserved; some models accept several reference images (Kling O3 up to 7, WAN 3.0 up to 10). The handoff artefact is therefore the **flattened composite**, with individual layers usable only as additional reference images where a model supports them.

## Candidate data models for a layered frame

### (i) Layer entity list per frame version (recommended)

Shape (per frame version):

```
frameVersion {
  id, frameId, parentVersionId, createdBy, createdAt,
  canvas { w, h },
  layers: Layer[]            // records keyed by id, sorted by rank
  composite { assetId, composedFromHash, stale: bool }
}
Layer {
  id, name,
  parentId: null | layerId   // reserved for groups; null for now
  rank: string               // fractional index, jittered, tie-break on id
  kind: background | object | text | effect
  source { kind: segmented | generated | filled | imported | drawn,
           provider, model, jobId, prompt?, parentAssetId?,
           modelBbox?, digitalSourceType }
  asset: assetId             // RGBA PNG, cropped to content
  mask?: assetId             // 8-bit, same size as asset
  transform { x, y, w, h, rotation }   // frame pixel space
  opacity, blend, visible, locked
  effects: Effect[]          // per-layer non-destructive adjustments (GIMP/Krita pattern)
  variants?: { assetId, jobId }[], activeVariant?
}
```

- **Undo.** Two levels, as Excalidraw and Figma do: in-session undo is an inverse-op stack over layer records (add/remove/field set, rank change); across sessions, the frame version chain is the durable history. Undo of a reorder is one field write (`rank`), undo of a delete re-adds the record (assets are never deleted with the record).
- **Collaboration.** Records keyed by id with LWW per field; `rank` is a jittered fractional string, ties broken by `id` and deduplicated on reconcile (Excalidraw PR #7359); if groups are added, store `parentId` and `rank` as one field so a reparent and its position update together (Figma 2019). No list-move operation is ever needed, so this works on Yjs maps, on Loro, or on a plain server-sequenced store.
- **Export.** ORA is a direct serialisation: each layer PNG to `data/`, `x, y, opacity, visibility, composite-op` to `stack.xml`, nested `stack` for groups, our composite as `mergedimage.png`. PSD via ag-psd: one layer per record with canvas, name, opacity, blend, mask, `lsct` groups; render the composite ourselves and set `psd.canvas`; rotation must be baked into the layer pixels because PSD raster layers have no rotation. C2PA on the flattened PNG/JPEG: one `componentOf` ingredient per AI layer, `c2pa.placed` with a pixel rectangle from `transform`, `compositeWithTrainedAlgorithmicMedia` on the asset.
- **Video handoff.** The cached composite is the Runway input; the record's `composedFromHash` (hash of layer ids, ranks, transforms, asset ids, effects) tells us whether to re-render before sending. Layers can be sent as extra reference images where a model accepts them.
- **Frame versioning.** A new version is a copy of the layer list with changed records; assets are content-addressed and shared across versions, so a version costs metadata plus any new pixels. Delayering an existing flat frame creates a version whose `background` layer is the inpainted base and whose `object` layers carry `source.kind = segmented`.
- **Rework risks.** Two models side by side (layer list and the existing edit list) unless the edit list is recast as the operation history of layer records; a stale composite if any write path forgets `composedFromHash`; groups later require a `parentId` migration (mitigated by reserving the field now); storing Seedream's cropped layers and Qwen's full-canvas layers in one shape needs a normalisation step at ingest (crop to alpha bounds and compute `transform`).

### (ii) Layers as a new edit kind in the existing non-destructive edit list

The frame stays "base image plus ordered edits"; a `delayer` edit yields layer ids, and later edits (`move-layer`, `reorder-layer`, `regenerate-layer`) reference them; rendering evaluates the list.

- **Undo.** Natural: truncate or disable list entries.
- **Collaboration.** An ordered list of edits that themselves reorder an ordered list. Appending edits merges fine; reordering or disabling an edit in the middle is the Yjs array-move problem again, and re-running an AI step that returns a different layer count invalidates every later edit that named a layer (the Figma Weave node graph has the same property and handles it by re-running the whole chain).
- **Export.** PSD/ORA require materialising the layers by evaluating the list; cheap if edits are per-layer transforms, expensive and lossy once edits include blends across layers.
- **Video handoff.** The evaluation result is the composite; same caching problem as (i) without a record to hang the hash on.
- **Frame versioning.** Unchanged.
- **Rework risks.** High. GIMP 3.0 and 3.2, Krita and Photoshop all ended at effects attached to layers with history as a separate concern; a global operation list as the model makes layer state implicit, so every UI (layers panel, locking, provenance per layer, C2PA export) has to re-derive it. Expect to migrate to (i) within a few features.

### (iii) A separate "layered image" document referenced by the frame

The frame holds a reference to a layered document and its version, plus the rendered composite; editing opens the sub-document (Photoshop smart object, Krita file layer, GIMP link layer, Figma Weave node).

- **Undo.** Separate stack per document, which users already understand from smart objects.
- **Collaboration.** A separate collaborative document, so no new ordering problems in the frame; the frame only updates the pinned version and composite.
- **Export.** The layered document is the ORA/PSD; the frame export is a flattened image unless we splice the sub-document's layers into the frame export.
- **Video handoff.** The frame's composite, as in (i).
- **Frame versioning.** Two version chains that must be pinned together (frame version → layered document version). Forgetting the pin makes old frame versions re-render with new layers.
- **Rework risks.** Medium. Right if the same layered image is reused across many frames or shared across projects (a product cutout used in ten frames), otherwise it adds navigation and a second versioning system for no gain. Keep it as a refactor path: (i)'s `frameVersion.layers` can later be lifted into its own document without changing the `Layer` record.

## What this means for Napkin

- Adopt (i): a flat list of layer records per frame version, keyed by id, with a jittered fractional `rank` and a nullable `parentId` reserved for groups. This is the shape Figma, tldraw and Excalidraw converged on and it maps one-to-one onto ORA.
- Keep the existing edit list as **history of operations on layer records** and attach non-destructive adjustments to the layer as `effects[]` (GIMP 3.x Fx, Krita filter masks), not as frame-level edits.
- Normalise AI outputs at ingest: Seedream gives cropped PNGs with `z_index`, bbox, name and description; Qwen gives full-canvas RGBA layers bottom to top. Store the cropped asset plus `transform` in frame pixels, keep the model's bbox and name in `source` for provenance, and set `rank` from the returned order.
- Treat the flattened composite as a cache with a `composedFromHash`; ORA requires it, PSD readers in the browser need it, and Runway accepts only flat JPEG/PNG/WebP (alpha handling unstated), so the composite is the handoff artefact.
- For ORA export, write layers at 100% opacity with opacity in `stack.xml`, map blend modes to the `svg:*` set and fall back to `svg:src-over`, and always write `mergedimage.png` and a 256 px thumbnail; for PSD use ag-psd (MIT, v31.0.3), render the composite ourselves, RGB 8-bit only, bake rotation into pixels.
- Record `source` per layer in C2PA terms from day one (`componentOf` ingredient, `c2pa.placed`, pixel rectangle, `compositeWithTrainedAlgorithmicMedia` on exports); it is cheap now and expensive to reconstruct later.
- Store variants on the layer (`variants[]`, `activeVariant`) rather than as sibling layers, as Photoshop's generative layer does, so a regenerate does not multiply layers.
- Do not depend on Adobe Layered Image Editing, Figma Weave's compositor or Recraft as references for shipped behaviour; the only decomposition APIs with documented output schemas today are Seedream 5.0 Pro Layerize (commercial, per-layer pricing) and Qwen-Image-Layered (Apache 2.0, self-hosted, 640-1024 px).

## Open questions

- Does Runway preserve or flatten alpha in PNG inputs? The inputs page does not say; a test with a transparent PNG decides whether cutout layers can be reference images.
- Does the existing frame versioning already content-address assets? If not, the per-version layer list duplicates pixels and (i)'s cost argument weakens.
- Is group support (nested stacks, pass-through blending) needed in the first release? It decides whether `parentId` is populated now or only reserved.
- Which blend modes does the canvas renderer support? ORA's SVG set and PSD's keys differ; the layer record's `blend` enum should be the intersection we can render and export.
- How are Seedream's `bounding_box.normalized` units defined (0-999 in the fal example, unstated)? Needed for the ingest normaliser.
- Should the C2PA manifest be written on every export or only when an AI layer is present? Adobe attaches automatically when generative tools were used; our policy should be explicit.
- Will layered images be reused across frames (product cutouts, brand marks)? A yes moves (iii) from "later refactor" to "design now".
- The Weavy Compositor's rule that layers fed by a connected node cannot be duplicated, and Canva's Magic Grab behaviour, were not readable at the primary source; both should be checked in-product before being cited in a design.
