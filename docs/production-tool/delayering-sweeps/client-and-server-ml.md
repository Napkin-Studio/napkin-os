# Running segmentation and fill-behind ourselves: browser, CPU, GPU

Sweep date: 2026-10-23. Angle: feasibility and cost of running the delayering ML ourselves under permissive licences.

Note on inputs: the brief at `scratchpad/delayering/brief.md` was not present when this agent ran (the directory was empty after the workflow restart). The research follows the angle text only. The product constraints assumed from the angle are: a permissively licensed product sold to external customers, canvas-first, expected to run on iPad as well as desktop, on AWS. Web search ran out of budget part-way; the second half of the sweep used direct fetches of primary sources only, so a few items are marked unverified.

## Short answer

Segmentation is solvable in the browser today with permissive weights: SAM 2.1 Hiera-tiny (Apache-2.0, 67 MB fp16 encoder plus 10 MB decoder), SlimSAM/MobileSAM/EdgeTAM (Apache-2.0, under 40 MB), and ISNet/BiRefNet-lite (Apache-2.0 / MIT, 44-213 MB) all have working ONNX paths and run in 0.1-0.8 s on desktop WebGPU and 2-6 s on WASM. The large BiRefNet (MIT, 520 MB fp16) only runs on WebGPU after graph surgery for the storage-buffer limit. Fill-behind in the browser is limited to MI-GAN (MIT, 29.5 MB, ~0.4-0.6 s per 512 tile) or LaMa (Apache-2.0, 198 MB, WASM-only because its Fourier convolutions compute wrong on the WebGPU EP, ~4 s per tile). Anything diffusion-class (Qwen-Image-Edit, Qwen-Image-Layered, FLUX.2 klein) is server GPU only.

Firefox ships WebGPU on Windows (141, July 2025) and Apple Silicon macOS 26 (145, Nov 2025) but not Linux or Android as of Firefox 157 (Sep 2026). Safari 26 (Sep 2025) ships it on macOS, iOS and iPadOS, but Apple exposes only 10 storage buffers per shader stage, iOS tabs get roughly 1 GiB max buffer and under 500 MB of practical tab memory, and the onnxruntime-web WebGPU bundles leak to ~5 GB and get killed on iPad under Safari 26.x. On iPad the safe path is small models on the plain WASM build, or the server.

On the server, CPU inference of BiRefNet-lite (2.4 s at 1024 on a laptop-class CPU) and LaMa (4.6 s at 1536 on 16 threads) costs well under a tenth of a cent per image on Lambda (10 GB, $0.0000166667/GB-s) or Fargate. A 20B diffusion model (Qwen-Image-Edit, 40.9 GB bf16 transformer plus 16.6 GB text encoder) needs a g6e.xlarge (L40S 48 GB, $1.861/h) with FP8/INT4 or a g6.xlarge (L4 24 GB, $0.80/h) with INT4 and offload, costs on the order of $0.01-0.05 per image at full utilisation and $0.05-0.50 at realistic 10-30% utilisation, and has multi-minute cold starts. Bedrock Custom Model Import only accepts decoder LLM architectures (Llama, Mistral, Qwen2/3, GPT-OSS, Flan) and is not usable for any of these models. SageMaker Serverless has no GPU and a 6 GB ceiling. Fargate has no GPU.

Licence picture: SAM 2, EdgeTAM, MobileSAM, SlimSAM, EfficientSAM, EfficientViT-SAM, U2-Net, DIS/ISNet, LaMa, simple-lama, BrushNet code, Qwen-Image-Edit, Qwen-Image-Layered, FLUX.2 klein 4B, OmniGen2 are Apache-2.0. BiRefNet (all variants), ViTMatte, MI-GAN (code and weights) are MIT. SAM 3 is under Meta's custom "SAM License" (commercial use not excluded, but redistribution must carry the licence and it has ITAR/military use restrictions, so it is not a permissive OSS licence). Blocked for a commercial product: SAM-family EdgeSAM (NTU S-Lab 1.0), MatAnyone (S-Lab 1.0), MAT (CC BY-NC 4.0), pix2gestalt (CC BY-NC 4.0), RMBG-2.0 (CC BY-NC 4.0), FLUX.1 Fill dev (non-commercial), ObjectClear (S-Lab 1.0), and the `@imgly/background-removal` ISNet exports (AGPL-3.0). SDXL inpainting, BrushNet and PowerPaint checkpoints inherit CreativeML OpenRAIL(++)-M from their Stable Diffusion base, which allows commercial use with use restrictions but is not a permissive licence; they can run server-side but cannot be redistributed inside a permissive client.

## 1. Browser in 2026

### 1.1 Runtimes

- Transformers.js v4 shipped on 9 Feb 2026 with a WebGPU runtime "completely rewritten in C++", about 200 architectures, a 4x speedup on BERT-class embedding models, `ModelRegistry` for cache inspection and `env.useWasmCache` for offline use. The same WebGPU code runs in Node, Bun and Deno. https://huggingface.co/blog/transformersjs-v4 (2026-02-09)
- The Transformers.js supported-model list includes SAM, Segment Anything 2, Segment Anything 3 and EdgeTAM, and a `background-removal` task. Default device in the browser is WASM; `device: 'webgpu'` opts in; the default dtype on WebGPU is fp32, on WASM q8. The docs still say "The WebGPU API is still experimental in many browsers". https://huggingface.co/docs/transformers.js/index (read 2026-10-23)
- ONNX Runtime v1.31.0 was released 9 Oct 2026 and is matched with WebGPU Plugin EP v0.5.0. The WebGPU EP is now a separately versioned library. Plugin EP v0.3.0 (Aug 2026) added deferred dispatch to parallelise shader compilation during cold start and exposed buffer-cache options through the JavaScript API; v0.4.0 (Sep 2026) scales pipeline-compilation workers with CPU count. https://github.com/microsoft/onnxruntime/releases (read 2026-10-23); https://github.com/microsoft/onnxruntime/releases/tag/v1.31.0 (2026-10-09)
- The onnxruntime-web WebGPU tutorial still says WebGPU is "available in Firefox behind a flag and Safari Technology Preview", which is stale; the npm page returned 403 to this agent, and jsDelivr shows 1.30.0 as the listed version (publish date not shown). https://onnxruntime.ai/docs/tutorials/web/ep-webgpu.html (read 2026-10-23); https://www.jsdelivr.com/package/npm/onnxruntime-web (read 2026-10-23)
- Chrome: WebGPU on desktop since 113; on Android 12+ with Qualcomm and ARM GPUs since Chrome 121 (18 Jan 2024). caniuse lists Chrome Android as fully supported from 156 and Samsung Internet from 24. https://developer.chrome.com/blog/new-in-webgpu-121 (2024-01-18); https://caniuse.com/webgpu (read 2026-10-23)

### 1.2 Firefox WebGPU state

- Firefox 141 (22 Jul 2025): "Enabled the WebGPU API" on Windows. https://www.firefox.com/en-US/firefox/141.0/releasenotes/ (2025-07-22)
- Firefox 145 (11 Nov 2025): "The WebGPU DOM API ... is now available on macOS 26 (Tahoe) on Apple Silicon." Intel Macs and macOS 15 or older are not covered. https://www.firefox.com/en-US/firefox/145.0/releasenotes/ (2025-11-11)
- Firefox 150 (21 Apr 2026), 153 (21 Jul 2026) and 157 (29 Sep 2026) release notes do not mention WebGPU, so no Linux or Android enablement was found through 157. caniuse marks Firefox desktop as "Disabled by default" through 161 (it does not split by OS) and Firefox for Android 158 as disabled. The Mozilla gfx blog's last WebGPU post is the Windows ship announcement of 15 Jul 2025. https://www.firefox.com/en-US/firefox/157.0/releasenotes/ (2026-09-29); https://caniuse.com/webgpu; https://mozillagfx.wordpress.com/ (read 2026-10-23). Linux/Android status: confirmed only by absence of a release note, so treat as "not shipped" with medium confidence.
- Firefox WebGPU performance is poor for ML even where shipped: "Llamas on the Web" measured a q4_k_m Llama at about 1 tok/s on Firefox versus 52 tok/s on Chrome on an Apple M3 and omitted Firefox from its evaluation. https://arxiv.org/html/2605.20706v1 (2026-05-20)

### 1.3 Safari, iOS and iPadOS

- Safari 26.0 (15 Sep 2025): WebGPU "is now shipping in Safari 26.0 for macOS, iOS, iPadOS, and visionOS." It requires macOS 26 / iOS 26; older OS versions have no `navigator.gpu`. caniuse marks Safari macOS as partial support through 27.1 TP and iOS as supported from 26.0. https://webkit.org/blog/17333/webkit-features-in-safari-26-0/ (2025-09-15); https://caniuse.com/webgpu
- Storage buffers per shader stage: web3dsurvey shows 100% of Safari reports at >=8 and 98% at >=10, iOS 99% at >=10, versus Chrome mostly 16 and Firefox mostly 31-48. So Apple exposes 10, which is above the WebGPU default of 8 but far below Chrome. https://web3dsurvey.com/webgpu/limits/maxStorageBuffersPerShaderStage (read 2026-10-23)
- Consequence 1: the stock onnx-community BiRefNet and BiRefNet-lite exports fail on Apple GPUs with "Too many storage buffers in shader. Current: 11, Max is 10"; the WASM fallback at 1024x1024 dies with `std::bad_alloc` because activations exceed the 4 GB wasm32 heap. RMBG-1.4 ran in 0.25 s on WebGPU and ~6 s on WASM on the same machine. https://dev.to/mno_tao_236ab4649edf4cf9f/three-things-that-broke-when-i-moved-ai-image-models-into-the-browser-4ai5 (posted Sep 28, year not shown; references Chrome 140 era)
- Consequence 2: onnxruntime-web created its device with the default limit of 8 rather than the adapter's 10, so `Concat` with 8 or more inputs silently returned zeros on WebGPU (onnxruntime-web 1.30.0, Apple M1). Fixed by PR #32783 on 25 Sep 2026; the fix's release version is not stated. https://github.com/microsoft/onnxruntime/issues/32757 (2026-09-23)
- Max buffer sizes: iOS reports maxBufferSize >=1 GiB in 81% of cases with no higher tier reaching a majority; maxStorageBufferBindingSize on iOS is >=644 MB in 95% and >=1 GiB in 81%. macOS Safari reaches ~2 GiB in 62-65%. Chrome reports ~2 GiB in 95%. https://web3dsurvey.com/webgpu/limits/maxBufferSize; https://web3dsurvey.com/webgpu/limits/maxStorageBufferBindingSize (read 2026-10-23)
- Tab memory: "On iOS, Safari tab memory is limited to under 500 MB" (Llamas on the Web, which also saw Transformers.js on Safari/M4 Pro grow to ~10 GB before the tab was killed, attributed to a likely leak between Transformers.js and Safari's WebGPU). https://arxiv.org/html/2605.20706v1 (2026-05-20). A separate JS-heap test crashed a page at ~100 MB on an iPhone SE 3 and ~200 MB on an iPad 8th gen on iOS 26.2 (both are 3-4 GB RAM devices). https://lapcatsoftware.com/articles/2026/1/7.html (2026-01-22)
- onnxruntime-web on WebKit 26: issue #26827 (opened 18 Dec 2025) reports Safari 26.2 looping in the OMG WASM JIT with memory growing to 14 GB on the JSEP build; versions 1.21+ affected, 1.20 unaffected. A 2 Sep 2026 follow-up on iPad (iPadOS/Safari 26.x, onnxruntime-web 1.29.0) found both the JSEP bundle and the native-WebGPU asyncify bundle climb to ~5 GB until the tab is killed; the plain WASM build was stable; Safari lacks JSPI so the suspension path is unavailable. A 19 Oct 2026 comment on iPadOS 26.6 / 1.30 reports WebGPU throughput dropping ~3x after about 10 s of sustained load (suspected GPU power throttling). https://github.com/microsoft/onnxruntime/issues/26827 (2025-12-18 to 2026-10-19)
- A SAM2 Next.js demo "Fails on iOS (17, iPhone SE), not sure why" and OPFS model storage does not work in Safari. https://github.com/geronimi73/next-sam (read 2026-10-23)

## 2. Our server on AWS

### 2.1 CPU: Lambda and Fargate

- Lambda limits: 128 MB to 10,240 MB memory ("At 1,769 MB, a function has the equivalent of one vCPU", so 10 GB is about 6 vCPU), 900 s timeout, container image up to 10 GB uncompressed, /tmp up to 10,240 MB, 6 MB synchronous payload (200 MB streamed). https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html (read 2026-10-23)
- Lambda price (x86, us-east-1): $0.0000166667 per GB-second, $0.20 per million requests, ephemeral storage above 512 MB at $0.0000000309 per GB-s. At 10 GB that is $0.000167 per second. Ireland price not shown on the page (unverified; historically identical). https://aws.amazon.com/lambda/pricing/ (read 2026-10-23)
- SnapStart supports Python 3.12+ (and Java 11+, .NET 8+) for zip and container images, "as low as sub-second" restores, but not with ephemeral storage above 512 MB; it bills snapshot caching (minimum 3 h) and restores. A pre-loaded ONNX session can live in the snapshot. https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html (read 2026-10-23)
- Fargate price (us-east-1): Linux/x86 $0.000011244 per vCPU-second ($0.04048/h) and $0.000001235 per GB-second ($0.00445/h); ARM $0.03238/h and $0.00356/h; Spot "up to 70%" off; no GPU anywhere on the page. Ireland not shown (unverified). https://aws.amazon.com/fargate/pricing/ (read 2026-10-23)
- Fargate has no GPU. ECS GPU task definitions require EC2 container instances (p3-p5, g4dn, g5, g6, g6e, g6f). https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-gpu.html (read 2026-10-23). A June 2026 AWS Builder post also states Fargate container definitions do not support the `gpu` parameter (secondary).
- Measured CPU latencies to size from:
  - BiRefNet_lite re-export (native DeformConv, onnxruntime >=1.20), Intel Core Ultra 9 185H: 2.4 s at 1024, 1.4 s at 768, 1.2 s at 640, 0.6 s at 512; stock export 6.5 s at 1024 with 10.5 GB peak RAM (the stock export will not fit a 10 GB Lambda). https://huggingface.co/senty-au/BiRefNet_lite-ONNX-dynamic (read 2026-10-23)
  - BiRefNet (Swin-L) 972 MB fp32, 1024x1024, Windows CPU provider: 9.2 s warm. https://github.com/jordanfelle/nicti/issues/349 (2026-09-30)
  - big-lama ONNX 1536x1536: ~4.6 s on 16 CPU threads; ~0.1 s on an RTX PRO 6000 (4 GB GPU memory peak). https://huggingface.co/smile-forge/big-lama-onnx (read 2026-10-23)
  - SAM 2.1 Hiera-tiny image encoder on CPU: no measurement found at a primary source; a 2026 fork reports 1082 ms for upstream Hiera-T in plain PyTorch on an RTX 5060 Ti at 1297x840 (GPU, not CPU). https://github.com/fastforks/sam2 (2026-10-12). Treat CPU encoder time as unmeasured (expect 1-3 s on 6 vCPU; inference).
  - Native BiRefNet on GPU for reference: 86.8 ms fp32 / 69.4 ms fp16 on A100 at 1024; ONNX SwinL ~165 ms, SwinT ~94 ms on A100; 17 FPS fp16 on RTX 4090 with 3.45 GB. https://github.com/ZhengPeng7/BiRefNet (read 2026-10-23)
- Cost per image on CPU (computed from the prices above, not measured end to end): BiRefNet-lite at 1024 on Lambda 10 GB at 3-5 s is $0.0005-0.0008; LaMa 1024 at ~3-5 s is similar; on a 4 vCPU / 16 GB Fargate task ($0.233/h) a 3 s job is $0.0002 at full utilisation and about $0.001 at 20% utilisation. Lambda cold start for a 1 GB image plus ORT session creation is several seconds without SnapStart (inference; no primary measurement found).

### 2.3 Sizing a 10-20 GB diffusion model

- Qwen-Image-Edit (and -2509, -2511) is 20B parameters, Apache-2.0; the bf16 transformer is 40.9 GB (9 shards) and the Qwen2.5-VL text encoder is 16.6 GB, so the full bf16 pipeline is about 58 GB and does not fit a 48 GB L40S without quantisation or offload. https://huggingface.co/Qwen/Qwen-Image-Edit/tree/main/transformer; .../text_encoder; https://huggingface.co/Qwen/Qwen-Image-Edit-2511 (read 2026-10-23)
- Qwen-Image-Layered has the same 40.9 GB bf16 transformer (5 shards). https://huggingface.co/Qwen/Qwen-Image-Layered/tree/main/transformer
- Reported 24 GB-card runs: RTX 4090 OOM in plain bf16 ("22.36 GiB allocated"); with NF4 4-bit transformer, CPU offload and the 4-step Lightning LoRA, ~14 s per edit (3.52 s/it) and 28 s checkpoint load; dual RTX 3090 ~7 s. No fp8 or 50-step timings in the thread. https://huggingface.co/Qwen/Qwen-Image-Edit/discussions/18 (2025-08-21 to 2025-09-16)
- Nunchaku INT4/FP4 Qwen-Image-Edit: per-layer offloading "only requires 3-4GB of VRAM"; pre-quantised 4- and 8-step Lightning variants; the examples switch to full `enable_model_cpu_offload` above 18 GB VRAM. No timings on the page. https://nunchaku.tech/docs/nunchaku/usage/qwen-image-edit.html (read 2026-10-23)
- Smaller permissive editors that fit an L4: FLUX.2 [klein] 4B (Apache-2.0, "as little as 13GB VRAM", 4 steps, multi-reference editing, claims sub-second end to end; inpainting not mentioned) https://huggingface.co/black-forest-labs/FLUX.2-klein-4B; OmniGen2 (Apache-2.0, ~17 GB VRAM natively, instruction-guided editing, weights 2025-06-16) https://huggingface.co/OmniGen2/OmniGen2
- Cost per image (computed; not benchmarked on these instances): on g6e.xlarge at $1.861/h ($0.000517/s), a 20 s few-step edit is $0.010 and a 90 s full-CFG 40-50 step edit is $0.047 at 100% utilisation. At a realistic 20-30% utilisation for a bursty single-tenant queue, $0.03-0.05 and $0.15-0.25; at 10%, $0.10 and $0.47. Spot takes 15-30% off. On g6.xlarge with INT4 the hourly rate is 43% of the L40S but offload slows each step; expect similar per-image cost. A LaMa-class fill on g6.xlarge (0.2-0.5 s per 1024 image, inference from the 0.1 s at 1536 on a much faster card) is $0.0001 per image at full utilisation and about $0.001 at 10%.
- Cold start: an EC2 GPU node must boot (1-2 min), pull a 10-20 GB container image and read ~20-58 GB of weights from EBS or S3 (gp3 at 125-1000 MB/s means 1-8 min for the weights alone), then compile; expect 3-10 min from zero (inference; no primary measurement found). SageMaker async gives no number and adds a 300 s cooldown in its own example. Keeping one warm g6.xlarge costs $580/month on-demand; one warm g6e.xlarge $1,340/month.

## What this means for Napkin

- Client-side segmentation is ready to build on permissive weights: ship SAM 2.1 Hiera-tiny (fp16, 78 MB total) or EdgeTAM through Transformers.js v4 for click-to-select, and ISNet or BiRefNet-lite (fp16, under 110 MB) for whole-subject cutouts. Expect 0.1-0.8 s on desktop WebGPU and 2-6 s on WASM; budget a 1-5 s first-run shader compile and hide it behind the upload.
- Do not ship stock onnx-community BiRefNet exports: they exceed Apple's 10 storage buffers per stage and the WASM fallback OOMs at 1024. Either use the wonfy re-export recipe (split Concat/Split to <=6 inputs, replace GatherND, fp16 with fp32 I/O) or stay on BiRefNet-lite at 512-768.
- iPad is server-first for now: iOS Safari gives under 500 MB of tab memory, ~1 GiB max buffer, no JSPI, and onnxruntime-web's WebGPU bundles are killed at ~5 GB on iPadOS 26.x while the plain WASM build is stable. On iPad run only tiny models (MobileSAM/SlimSAM-class decoder, MI-GAN) on WASM, and send segmentation of large images and all fill-behind to the server.
- Firefox is Windows and Apple-Silicon-macOS only for WebGPU; treat Firefox on Linux and Android as WASM-only until a release note says otherwise.
- Fill-behind in the browser is MI-GAN (MIT, 29.5 MB, sub-second) for small holes; LaMa works but WASM-only at ~4 s per 512 tile. Anything that needs semantic completion of a large occluded region (true "fill-behind" of a removed layer) is a server GPU job.
- The cheapest server design is CPU for segmentation and LaMa (Lambda 10 GB or Fargate, well under $0.001 per image, seconds of latency) plus a scale-to-zero GPU queue for diffusion fills. For the GPU tier, g6.xlarge (L4 24 GB, $0.80/h) with FLUX.2 klein 4B or INT4 Qwen-Image-Edit, or g6e.xlarge (L40S 48 GB, $1.86/h) with FP8 Qwen-Image-Edit/Layered; expect $0.03-0.25 per image at realistic utilisation and 3-10 minute cold starts from zero, so keep a warm instance during working hours ($580-1,340/month) or accept the wait.
- Bedrock Custom Model Import, SageMaker Serverless and Fargate are not options for any of these models (LLM-only architectures, no GPU, no GPU respectively). SageMaker Async is the only managed scale-to-zero GPU path on AWS; it carries a 300 s cooldown pattern and no documented scale-up latency.
- Licence hygiene: keep every weight in the client to Apache-2.0/MIT (SAM 2, EdgeTAM, SlimSAM, MobileSAM, ISNet from the DIS repo, U2-Net, MI-GAN, LaMa). Keep SAM 3, OpenRAIL-based inpainters and the 20B Qwen models server-side and record their licences in the service's NOTICE. Never pull `@imgly/background-removal` (AGPL-3.0), RMBG-1.4/2.0, MatAnyone, EdgeSAM, MAT, pix2gestalt, ObjectClear or FLUX.1 Fill dev into the product.

## Open questions

- BiRefNet training data: the MIT licence covers weights and code, but BiRefNet's general models were trained on DIS5K (and others) whose terms-of-use PDF was not readable in this sweep; one re-exporter states DIS5K "restricts commercial use of the dataset". Whether dataset terms taint weights is a legal question for counsel; the same applies to ViTMatte (Composition-1k, Adobe) and LaMa (Places).
- Measured SAM 2.1 encoder time in a browser on WebGPU was not found at any primary source; it needs a bench on a Mac, a Windows laptop and an M-series iPad (WASM) before committing to click-to-select latency targets.
- Qwen-Image-Edit and Qwen-Image-Layered timings on L4 and L40S at INT4/FP8 are unmeasured; the only numbers are 4090-class (14 s at 4 steps with offload). Qwen-Image-Layered quality at 640 versus 1024 and its behaviour on photographic versus design inputs is untested.
- eu-west-1 on-demand and spot prices for g6.xlarge and g6e.xlarge were paywalled on every aggregator reached; Lambda and Fargate Ireland prices were not shown on the AWS pages fetched. Pull them from the AWS price-list API before costing.
- Whether the onnxruntime-web fix for the 8-vs-10 storage buffer device limit (PR #32783, 25 Sep 2026) is in a shipped onnxruntime-web/Transformers.js release, and whether the WebKit OMG JIT regression (#26827) is fixed in Safari 26.3+.
- Firefox Linux/Android WebGPU: confirmed only by absence from release notes through 157; check the Firefox 158-161 notes and the Bugzilla meta bug.
- Amodal completion with a permissive licence: nothing found with released permissive weights; the zero-shot approach (SAM mask plus a permissive inpainter, as in k8xu/amodal) would have to be built in-house.
- Whether ECS Managed Instances supports g6/g6e capacity (would simplify a scale-to-zero GPU pool versus hand-rolled ASG), and real scale-from-zero latency for SageMaker Async with a 20-58 GB model.
