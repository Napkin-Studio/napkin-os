## 1. Answer in ten lines

1. Pencil's delayering is trypencil's (Pencil AI, Brandtech). The owner's link (2026-10-23) is a LinkedIn post of 2026-10-21, "Delayering is now a thing! One image. Every layer editable.": any image is converted into separate editable layers for typography, design elements, subjects and backgrounds, each editable on its own, "powered by ByteDance's Seedream 5". That is Seedream 5.0 Pro's layer separation (Layerize, row below) behind Pencil's UI. The demo link leads to trypencil.com/contact; no docs, limits or pricing are public. pen.dev (the design tool) has no such feature, and "Pencil Studio" does not exist.
2. The capability is real and crowded: Lovart Edit Elements (Nov 2025), Qwen-Image-Layered open weights (Dec 2025), Canva Magic Layers (Mar 2026 beta), ByteDance Seedream 5.0 Pro layer separation (Jul 2026, API as "Layerize" Aug 2026), Luma Layers (Jul 2026), Magnific One Auto Layers (Oct 2026; magnific.com returned 403, so secondary only). Adobe announced Layered Image Editing in Oct 2025 and has not shipped it.
3. The 2026 baseline is one action, model-named layers in a z-stack with the background at the bottom, the hole behind each object filled in, per-layer regenerate, and $0.20-0.50 per extraction at 1-2K. Live text comes back from Canva, Luma and Lovart, and text-only layerising from Ideogram and Playground; Seedream, Qwen, OpenArt and the converters return a picture of the words.
4. For us the model layer is a commodity and the product work is the canvas, the layer record and export. Four approaches exist: generate per layer then composite (A), generate then segment and fill behind (B), native layered generation (C), and generate once then re-generate as layers conditioned on the image (D). C is closed or non-commercial everywhere; D is the field's current answer but re-synthesises pixels and needs a server GPU; B is the only fully permissive route that runs today on CPU or in the browser.
5. On the Runway API there is no layer, segmentation or background-removal primitive. The usable pieces are `gpt_image_2_5_sunburst` with `background: "transparent"` (generative alpha), `ideogram_4_5` with `maskUri` (black = edit, our mask, fill behind) and the flat Seedream 5 models. Runway's web app does have Seedream 5.0 Pro Layers (18 credits) and BiRefNet v2 (1 credit), so the gap is API exposure, which is a concrete ask.
6. Permissive open weights that we can run: SAM 2.1, EdgeTAM, SlimSAM, MobileSAM (Apache-2.0), BiRefNet and MI-GAN (MIT), LaMa (Apache-2.0 code; weights licence disputed), LayerD (Apache-2.0, CPU) and Qwen-Image-Layered (Apache-2.0, 20B, 72 GB bf16, 213 s at 1024 px on an H200). The FLUX.1 [dev] family, ART, Qwen-Image-2.1 and every shadow-aware decomposer are blocked.
7. In the browser, segmentation runs in 0.1-0.8 s on desktop WebGPU and 2-6 s on WASM; fill-behind is MI-GAN only. Firefox has WebGPU on Windows and Apple-Silicon macOS 26 only, and where it has it ML throughput is about a fiftieth of Chrome's, so the browser tier gates on a first-run timing of the SAM decoder rather than on WebGPU being present; iPad Safari 26 kills onnxruntime-web's WebGPU bundles at about 5 GB, so iPad is tiny models on WASM or the server.
8. Video: no 2026 route turns a clip into movable layers. The video analogue is "re-render the clip with this layer's content changed" through `aleph2` (28 credits/s, 56 minimum), `klingO3_*` video_to_video (whose Runway request shape for references and elements is unverified: the repo's catalogue lists `references` of 4 images or fewer from the OpenAPI snapshot, the sweep found no element or tag structure in either SDK, and the catalogue's Q10 is the open test) or `product_swap`; none returns alpha.
9. Data model: a layer record list per frame version, keyed by id with a fractional `rank` and a signed frame-pixel transform (so a layer can sit off the frame, which `common.region` cannot express), the composite kept as the frame's `asset`, per-layer assets with `origin: extracted` (planned in the approved record, not yet in the shipped schema), and the existing `edits[]` as history. It maps one to one onto OpenRaster and onto ag-psd (MIT) for PSD, and onto C2PA 2.2 `componentOf` ingredients for provenance.
10. Recommended: build the layer record and the permissive cut-out tier (B) first, with Runway `ideogram_4_5` fill-behind as the paid quality step, and keep the decomposer swappable so D (Qwen-Image-Layered self-hosted on our AWS, or Seedream layers through Runway if it exposes them) can slot in once an FP8 run on g6e.xlarge has been measured. The owner's two hypotheses are A (generate each layer, then composite) and D (generate once, then make the layers from that image in the background), so the verdict in section 3 applies as written. The main risk is quality on the hard cases every vendor warns about: shadows left behind, hair, glass, overlapping objects and text; the floor tier does not complete occluded parts, and the only models that do need a GPU and re-synthesise the user's pixels.

## 3. The four approaches

The owner's two hypotheses (2026-10-22): first, generate the layers of the image individually and superimpose them, which is A below; second, generate the image first, then in the background take it as the reference and generate its layers, which is D below (B is its cheaper, non-generative form). The verdicts cover all four.

### A. Per-layer generation, then composite

- **How it works.** Each element is generated on its own with an alpha channel, placed on the canvas, and composited; a harmonisation or relighting pass can follow. Alpha sources: `gpt_image_2_5_sunburst` with `background: "transparent"` on Runway (and `gpt_image_2`, whose `transparent` enum reflects OpenAI's 2026-08-20 preview; Runway's proxy is untested), LayerDiffuse on SDXL self-hosted (CreativeML OpenRAIL-M, 8 GB VRAM; server-only, pending the OpenRAIL ruling in section 9). Runware's LayerDiffuse on FLUX Dev and Alibaba Model Studio `qwen-image-2.1-pro/turbo` (alpha when the prompt asks) also return alpha, but as non-Runway APIs they are not available under the provider rule and are listed for reference only.
- **Evidence of quality.** LayerDiffuse's user study preferred native transparency over generate-then-matte in 97% of cases (2024). GPT Image 2 transparent PNGs carry alpha of 252-254 instead of 255 and a thin grey halo (OpenAI community user reports, 2026; secondary). Google's image models document no alpha at all; practitioners generate on #00FF00 and key it. No paper benchmarks A against B or D for whole compositions; the coherence problem (light, perspective, scale between separately generated elements) is the reason MRT, LASAGNA and Luma generate layers jointly, and ART's user study lost to COLE on typography.
- **Latency.** One Runway call per element, roughly 40 s for a Sunburst image in the repo's own pathway tests (docs/production-tool/pathway-tests-2026-10-13.md, not a sweep finding), parallel up to the account's concurrency.
- **Cost per image.** Sunburst high: 16 credits plus 1 per reference per output, so about $0.17 per element; six elements about $1.00. `gpt_image_2` low: 1-2 credits per element. Harmonisation on CPU (PCT-Net, MPL-2.0) costs nothing material.
- **Failure modes.** The pasted-on look (the recurring Midjourney layers complaint), inconsistent lighting and shadows, alpha fringes, scale and perspective drift, text rendered per element unreliably, and cost that grows with element count. It cannot "delayer" a frame the user has already approved; it only makes new frames.
- **Afterwards.** Everything is a native layer: move, hide, regenerate one element, swap a product; brand type can be set by us as real text rather than recovered.
- **What it needs that we lack.** A layout-planning step (which elements, where), a harmonisation pass (PCT-Net on CPU; IC-Light v1 is OpenRAIL-M; IC-Light V2 and LBM are non-commercial), shadow synthesis (GPSDiffusion, MIT, "unstable" per its authors), and an alpha-normalise and de-fringe step for every source.

### B. Generate, then decompose: segment plus fill-behind

- **How it works.** The flat frame is detected (Florence-2, MIT; Grounding DINO, Apache-2.0), masked (SAM 2.1, Apache-2.0, from clicks; BiRefNet, MIT, for the whole subject), the hole is filled (MI-GAN, MIT, or LaMa, Apache-2.0 code, on CPU or in the browser; or `ideogram_4_5` `maskUri` on Runway; or Qwen-Image-Edit on a GPU), and each cut-out becomes an RGBA layer over the filled base. LayerD is this loop made iterative for graphic designs (BiRefNet matting fine-tuned on Crello, LaMa fill, at most 3 iterations in the paper, inputs resized to a 512 shorter side in the experiments, SVG and PSD export in the Apache-2.0 repo).
- **Evidence of quality.** On Crello (merge 0) LayerD scores alpha soft IoU 0.7520 and RGB L1 0.0709 against Qwen-Image-Layered-I2L's 0.8705 and 0.0594. On LICA, LayerD has the highest pixel PSNR (37.22, against PixelART 36.39 and Qwen 31.99) and the lowest VLM visual score (3.64 against 4.44 and 3.93): precise but less plausible layers. LayerD's appendix found FLUX.1 Fill as the filler "often introduces unwanted objects", which is why it uses LaMa. Product evidence: RunDiffusion ships SAM-style segmentation without inpainting; Photoroom "sometimes places multiple parts of an image on a single layer" and the fix is manual.
- **Latency.** Browser: 0.1-0.8 s per segmentation on desktop WebGPU, 2-6 s on WASM; MI-GAN about 0.4-0.6 s per 512 tile. Server CPU: BiRefNet-lite 2.4 s at 1024 px (Core Ultra 9 laptop class), LaMa 4.6 s at 1536 px on 16 threads. Runway fill: `ideogram_4_5` masked edit took 47 s in the repo's pathway tests. A whole-frame "Split into layers" adds up step by step: detection on the relay CPU (Florence-2 or Grounding DINO; no CPU latency is published, so it must be measured), then one mask pass per object (0.1-0.8 s on desktop WebGPU, 2-6 s on WASM or iPad), then MI-GAN over every hole (0.4-0.6 s per 512 tile; a 1-2K frame is 4-16 tiles, so 2-10 s for a pass over the frame). Six to ten objects is a few seconds on a desktop WebGPU machine and tens of seconds to about a minute on WASM or iPad, so the whole-frame split is a job through the send tray and the busy pointer like the others (section 6); only a single click-select or Remove background is immediate.
- **Cost per image.** Under $0.001 per image on Lambda 10 GB or Fargate CPU; $0 on the device. Runway fill-behind: 8 credits per masked edit at medium quality (4 at low, 25 at high), once per hole or once for a merged mask.
- **Failure modes.** No amodal completion: a layer is only the visible fragment. Shadows and reflections stay baked into the background (orphan shadows under a moved object). The fill is a guess, not a recovery. Overlapping or same-colour objects merge; hair, glass and smoke give soft edges; errors compound across iterations (LayerD's stated limitation); very small text fails.
- **Afterwards.** Move, hide, reorder, delete; edit the base; regenerate one layer on Runway from references; save a cut-out as a ref (the Image editor already specifies "Save as reference"). Text stays raster unless we OCR and re-set it.
- **What it needs that we lack.** Nothing licence-blocking. We need a layer record (section 6), the worker ML with a server fallback (the Image editor spec already says Remove background "uses the relay automatically when WebGPU is missing or memory is low"), a mask-to-`maskUri` bridge and paste-back resize (Ideogram returned 2695x1536 for a 2752x1536 input in the pathway tests), and a decision on LaMa versus MI-GAN (LaMa's big-lama weights have no licence text and an open issue about Places2 terms; MI-GAN's weights carry an explicit MIT grant). Amodal completion and shadow layers have no permissive weights at all (pix2gestalt CC BY-NC, SynergyAmodal CC BY-NC-SA, LayerDecomp and ObjectDrop unreleased, ObjectClear S-Lab non-commercial).

### C. Native layered generation

- **How it works.** The model emits layers from the start: Luma Uni-1, Canva Design Model, Canva Research's MRT (CVPR 2026), Adobe's LASAGNA, Microsoft's ART.
- **Evidence of quality.** MRT reports image-to-layers user-study win rates against Qwen-Image-Layered of 79.5% (layer quality), 68.9% (integrity) and 82.6% (granularity) on 100 out-of-domain designs, about 108.5x faster at about 20 layers and 10.5-23.6x lower peak memory, with 2-50 layers and off-canvas overflow; it admits shadows "often stay on the background layer" and limited photorealistic generalisation. ART's 30-person study preferred it over LayerDiffuse and COLE on most axes but trailed COLE on typography. Luma's and Canva's claims are vendor statements with no published numbers.
- **Latency.** MRT: about 6 s for a 1K image with about 20 layers on one H100 (about 5 s in a figure caption; about 3 s on 4x H100). Luma: not stated.
- **Cost per image.** Luma 75-175 credits ($0.23-0.53 at the Plus rate). Nothing on Runway.
- **Failure modes.** Not available to us: MRT and LASAGNA have no code, weights or demo as of 2026-10-23; ART's weights were withdrawn on 2025-07-23 because the training data "may have come from illegal sources"; ART+, CLD, SynLayers, AlphaVAE, LayerDiffuse-Flux and OmniPSD are FLUX.1 [dev] derivatives under the FLUX [dev] Non-Commercial License (v2.0, revised 2025-11-25, covers the whole FLUX.x [dev] family). Qwen-Image-2.1 (7B, native RGBA, Sep 2026) is under the Qwen Research License, "FOR NON-COMMERCIAL PURPOSES ONLY".
- **Afterwards.** The best editing surface in the market (live text at Luma and Canva, per-layer regenerate without touching the rest), which is why it sets user expectations.
- **What it needs that we lack.** A model. The likeliest future permissive candidates are PixelART (1.05B, trained from scratch so no base-model licence to inherit, weights not promised) and LiWi (request-only today).

### D. Hybrids: generate once, then re-generate as layers conditioned on the image

- **How it works.** A diffusion decomposer takes the flat image and emits N RGBA layers, including an inpainted background: Qwen-Image-Layered (full-canvas RGBA layers, bottom to top, any layer decomposable again), Seedream 5.0 Pro Layerize (base plus up to 16 cropped PNGs with z_index, bbox, name and description), Lovart Edit Elements (observed to "regenerate the image"), OmniPSD (unreleased).
- **Evidence of quality.** Qwen-Image-Layered-I2L on Crello: RGB L1 0.0594, alpha soft IoU 0.8705 (merge 0). PixelART's Design-Multi-Layer-Bench: composite PSNR Qwen 32.46 against LayerD 36.07 and PixelART 36.92; VLM visual 4.14/4.37 against 3.49/3.13 and 4.57/4.81. LiWi and PixelART both report Qwen-Image-Layered is weaker on photographs than on designs (it was trained on PSD-derived layers). ByteDance's demo splits a poster into more than 10 layers with the background "inpainted and restored" (vendor demo). Replicate describes Qwen's output as "foreground, background, and shadow layers" while DataCamp (secondary) saw shadow remnants left on the background: treat shadow handling as unproven.
- **Latency.** Qwen-Image-Layered: 213.4 s at 1024x1024 on one H200 (PixelART's measurement, 100 images); latency grows with layer count (MRT); one user report of a 24 GB RTX 4090 hanging for over 8 hours at 0% (issue #30, anecdotal, no replies); Replicate's own example run on the saved page (the saved Replicate page (2026-10-23), primary): go_fast, 4 layers, default settings, `predict_time` 7.94 s on an Nvidia H100; DataCamp reports 30-60 s on Replicate (secondary; fal's default is 28 steps against the card's 50). So the time per image spans two orders of magnitude by steps, resolution and distillation: 7.9 s for a few-step H100 run against 213 s for 50 steps at 1024 px in bf16. Seedream Layerize: about 120 s per request. Standalone converters: 45-120 s at 1K.
- **Cost per image.** Hosted prices first, for reference only, since fal, Replicate and BytePlus are not available under the provider rule: fal `fal-ai/qwen-image-layered` $0.05 per image for 1-10 layers, stated on fal's own model page (the sweep's "only secondary" label was refuted); Replicate `qwen/qwen-image-layered` $0.03 per run plus $0.01 per output image with go_fast and $0.07 plus $0.01 without, confirmed in the `billingConfig` of the saved page (the saved Replicate page (2026-10-23); hardware Nvidia H100; `num_layers` 2-8, default 4; an earlier check that found no price on the public page is superseded); Seedream direct on BytePlus $0.25-0.41 for a 10-16 layer split depending on which reading of the price list is right. Runway web app: 18 credits ($0.18) per Pro Layers run, not on the API. Self-hosted, by configuration, because no L40S measurement exists: (a) 50 steps at 1024 px in bf16 is 213 s and 72.4 GB peak on an H200 (PixelART), which does not fit a 48 GB L40S in bf16 at all and needs an 80 GB card or the FP8 checkpoint, whose fit in 48 GB is computed and not benchmarked; the earlier figure of about $0.11 per image at full utilisation and $0.37-1.10 at 10-30% applied that H200 time to the L40S rate of $1.861/h, a card several times slower, so it is a lower bound at best and not a cost line; (b) a few-step run at 640 px (fal's default is 28 steps; Replicate's go_fast example took 7.9 s for 4 layers on an H100) lands near the client-and-server sweep's generic 20B estimate of $0.01-0.05 per image at full utilisation and $0.05-0.50 at 10-30%, if FP8 on an L40S stays within a few times the H100 time. Neither is measured; running Qwen-Image-Layered FP8 on a g6e.xlarge at both settings is the gating step before Option 3 is costed (section 7).
- **Failure modes.** The layers are re-synthesised, not the user's pixels: fidelity drift, and the possibility of changed words (Canva's April 2026 word substitution is the warning case). Non-deterministic grouping between runs. Shadow remnants. Qwen's recommended bucket is 640 px (1024 is the other bucket), so resolution is lost. Seedream fails the whole request if any layer fails (BytePlus doc excerpt, unverified at primary; whether a failed request is refunded is a reseller statement, not confirmed). Slow enough that the UX must be an asynchronous job.
- **Afterwards.** As B, plus a filled background and (Qwen) recursive decomposition of any layer.
- **What it needs that we lack.** A GPU service on our AWS: an 80 GB card for bf16, or a 48 GB-class card with the FP8 checkpoint (fit computed, not benchmarked), or 24 GB with INT4 and offload (unmeasured, one 4090 hang report); or Seedream layers through Runway once exposed (Q10 in section 8). fal, Replicate and BytePlus host the same models but are not available under the provider rule, so they are not an option; an ingest normaliser (full-canvas RGBA to cropped asset plus transform); a fidelity check that diffs each layer's composite against the source; and an async job surface with a refund path.

### Verdict on the owner's two hypotheses

- **A, per-layer generation then composite: partly right, for new frames only.** It is the right path when we own the layout and the type, because brand text is then real text and each element is a native layer from birth. It is the wrong path for "delayering" an approved frame: it cannot recover that frame, and separately generated elements need a harmonisation and shadow pass we would have to build from thin permissive options (PCT-Net, GPSDiffusion). Treat it as the "generate as layers" entry, not the delayering feature.
- **D, generate once then re-generate as layers conditioned on the image: right about the field, wrong about the cost of entry.** Seedream, Qwen-Image-Layered and Lovart all work this way and it gives the best quality we can reach today, with the hole filled. But the only permissive model is a 20B network that needs a 48 GB-class GPU, takes minutes at 1024 px, and re-synthesises pixels, and it is not on Runway's API. It belongs behind a swappable `delayer` backend and an async job, after the GPU budget question in section 9 is answered and the FP8 measurement in section 7 is in.
- **B is the floor to ship first, C is not available.** B is fully permissive, runs in the browser or on CPU for under a tenth of a cent, and already matches the Image editor's cut-out and mask tools; its honest limits (no amodal completion, shadows left behind) are the same limits most shipped converters disclose. C exists only inside Luma, Canva and unreleased papers.
- **On "in the background".** The owner's second idea runs the decomposition by itself after every generation. Section 7 recommends an explicit action through the send tray instead: an automatic split costs a Runway fill or a GPU run for every generated frame and picture, most of which are never edited, and it needs the async job, refund and fidelity-diff surfaces before the first layer is useful. The free part of the cut-out tier (detection and masks on the relay CPU, no fill) is cheap enough to run by itself after a generation and makes the first click-select instant; that is the form of "in the background" worth keeping (section 9, question 9).

### 4c. In the browser, with the 2026 Firefox and iPad reality

- **Runtimes.** Transformers.js v4 (2026-02-09) lists SAM, Segment Anything 2 and 3, EdgeTAM and a `background-removal` task; default device is WASM, `device: 'webgpu'` opts in. ONNX Runtime 1.31.0 (2026-10-09) ships WebGPU as a separately versioned plugin EP (v0.5.0).
- **Chrome.** WebGPU on desktop since 113 and on Android 12+ (Qualcomm and ARM GPUs) since 121.
- **Firefox.** WebGPU shipped on Windows in 141 (2025-07-22) and on Apple-Silicon macOS 26 in 145 (2025-11-11). No Linux or Android enablement appears in the release notes through 157 (2026-09-29); caniuse marks desktop "disabled by default" through 161 and Android 158 disabled. Treat Firefox on Linux and Android as WASM-only. Where it is shipped, ML throughput is poor (about 1 token/s against 52 on Chrome in one M3 LLM measurement), so WebGPU presence is the wrong gate for Firefox: treat Firefox with WebGPU as WASM-or-relay until a first-run timing of the SAM decoder on that machine says otherwise, and put Firefox on Windows in the prototype matrix (section 7).
- **Safari, iOS, iPadOS.** WebGPU shipped in Safari 26.0 (2025-09-15) on macOS, iOS, iPadOS and visionOS, requiring OS 26. Apple exposes 10 storage buffers per shader stage (Chrome 16, Firefox 31-48): stock onnx-community BiRefNet exports fail with "Too many storage buffers in shader. Current: 11, Max is 10", and the WASM fallback at 1024 px dies with `std::bad_alloc` (4 GB wasm32 heap). onnxruntime-web also created its device at the default limit of 8, so `Concat` with 8+ inputs silently returned zeros (fixed in PR #32783, 2026-09-25; release version not stated). iOS tabs get about 1 GiB max buffer and under 500 MB of practical memory; on iPadOS 26.x both onnxruntime-web WebGPU bundles climb to about 5 GB and are killed while the plain WASM build is stable; a 2026-10-19 report sees WebGPU throughput drop about 3x after about 10 s of load. Conclusion: iPad is tiny models (MobileSAM or SlimSAM-class, MI-GAN) on WASM, or the server.
- **Measured speeds.** ISNet fp16: about 100-360 ms on WebGPU (M3 Max, M4), about 2 s on WASM with SIMD and threads (53 s single-threaded without SIMD). BiRefNet Swin-L fp16 re-exported for WebGPU: about 800 ms warm on an RX 9070 XT, 4.3 s load. BiRefNet-lite: about 5.3 s at 640x480 on Apple WebGPU (secondary, unverified). SAM v1 quantised encoder on WASM (2023): 30-60 s; WebGPU was 19x faster on the encoder in Microsoft's 2024 measurement. SAM 2.1 Hiera-tiny: no browser timing at any primary source. SAM 3 INT8 (888 MB) on WASM: 94.7 s. MI-GAN 512: about 0.6 s per tile on WASM, 2.1-3.5 s dropping to about 0.4 s on WebGPU after shader warm-up. LaMa fp32: about 4.3 s per 512 tile on WASM; INT8 drops masked PSNR from 28.9 to 17.8 dB; fp16 needs BatchNorm rescaling.
- **Download sizes.** SAM 2.1 tiny fp16: 67 MB plus 10.5 MB (q4f16 28.5 MB plus 4.6 MB); ISNet 84-88 MB fp16; BiRefNet-lite about 213 MB fp32; BiRefNet Swin-L 490-520 MB fp16; MI-GAN about 29.5 MB; LaMa 198-209 MB; U2-Netp 4.7 MB.
- **Known traps.** First-run shader compilation of 1-5 s (hide behind the upload); onnxruntime-web loads the whole model into WASM memory before copying to the GPU; fp16 BiRefNet exports collapsing to all-zero masks; a tab crash writing a 198 MB model to IndexedDB in one chunk; OPFS model storage not working in Safari.

## 5. Video: can layers carry into clips?

No. Every method that turns a clip into per-object RGBA layers with shadows and reflections (Generative Omnimatte, CVPR 2025; OmnimatteZero, SIGGRAPH Asia 2025; EasyOmnimatte, CVPR 2026; LayerFlow) runs for minutes per clip on a 48 GB-class GPU, needs object masks as input, and is non-commercial (OmnimatteZero: "may not be used for commercial purposes", including a paid service), unreleased (EasyOmnimatte, LayerFlow) or an Apache-2.0 reimplementation that admits it "does not match" the paper (gen-omnimatte-public: 1-2 min on an A100 plus about 8 min of optimisation per layer). None is a hosted API.

What exists is in-context re-rendering, and the layer vocabulary maps onto the edit types vendors sell: swap product, replace subject, remove distraction, change background, relight. A positional "move this layer 20% left" has no first-class control anywhere. On the Runway API:

## 6. Data model and UX

### What the approved record plans, and what the shipped schema has

From `features/contract-v3.clan` (approved by Shrey; the plan, read with `clan read agent`), `production-tool/contracts/*.schema.json` (what is shipped today) and `docs/production-tool/overhaul-plan.md` (the op list). The three are at different stages and the text says which is which:

- The approved record plans `frames` as an id-keyed map: `{shot_id? or sketch_id? or size_id?, version, parent_id?, kind generated|mock|edited, asset, job_id?, crew, model?, provider?, edits[] (64 or fewer), cropped_to?}` (record line 846). Every entity carries `v` and `field_v`; `rank` is the only order anywhere; `frames.selected` is gone in favour of `shots.pick {current, alternates[]}`.
- The record plans `assets` keyed by sha256 with `{kind image|video|audio|document|font|vector, mime, origin uploaded|drawn|generated|mock|edited|extracted}` (record line 853); the shipped `document.schema.json` has `origin` as `uploaded|drawn|generated|mock` today, with no `edited` and no `extracted`, so `extracted` arrives with the v3 batch. Both have `locations` (`idb://`, `s3://`, `https://`) and a webp `thumb`. Assets are already content-addressed in the shipped schema, which answers the data-model sweep's open question and makes per-version layer lists cheap.
- `refs` is `{key, variant, role, label?, asset? (image roles), swatches?, font?, rule?, library?}`; refRole is an 18-value set.
- `jobs` is `{op, state (adds needs_input), node {kind,id}, purpose, started_by, tenant_id, nonce, crew, inputs[], region?, text?, chips?, ask_id?, parent_ids, input_hashes, outputs, director, cost, error?, ...}`; the shipped `common.schema.json` has `op` as `generate|view|shot_list|frame|region_edit|clip|clip_edit|stitch` and `quotaClass` as `image|video|render|text`; the overhaul plan, not the record, adds `frame_edit`, `clip_patch`, `bridge`, `cutout` and `transcribe` as ops and lists Magnific upscale as a paid route (`overhaul-plan.md`, the op lines and the provider table); neither has a `delayer` op, which needs an op value and a `quotaClass` value (`image`, if a split is metered like a region edit, or a new per-layer class); `common.region` is a 0-1 box with a top-left origin, clamped to the frame.
- The Image editor (docs/production-tool/ui-behaviour.md 3.12) keeps edits as a non-destructive list ("Edits · not applied yet"; "Nothing is sent until you run an action. v3 is never changed"), numbered with their own undo; layers are listed front first: Text, masks, cut-outs and Frame (the locked input version); each layer can be hidden; a cut-out offers Save as reference; a result "lands as a new layer in the op list"; Apply saves v(n+1) as `kind: edited`, leaves v(n), makes it the shot's current frame in one undo step and marks the clip stale. Remove background runs on the device and falls back to the relay.

### Candidate shapes

Three shapes, with how undo, collaboration, export and versioning work for each. The shared evidence from mature editors: GIMP 3.x, Krita, Photoshop, Penpot, Polotno, tldraw and Excalidraw all model layered images as a flat or shallow tree of layer records, each with its own pixel asset, transform, opacity, blend, visibility and optional mask, with non-destructive adjustments attached to the layer; collaborative tools order siblings with a jittered fractional-index string tie-broken on the record id (Figma 2017 and 2019, Excalidraw PR #7359, tldraw, Loro), so a reorder is a single-field write. OpenRaster matches this one to one (per-layer PNGs, `stack.xml` with `x, y, opacity, visibility, composite-op`, nested stacks, mandatory `mergedimage.png`); PSD write is available under MIT via ag-psd v31.0.3 provided we render the composite ourselves (RGB 8-bit only, rotation baked into pixels).

**(i) Layer records on the frame version (recommended).**

```
frames.<id> {
  ...as v3...,
  asset: sha256            // the composite, cached, kept in step; what every reader and Runway sees
  composed_from?: sha256   // hash of (layer ids, ranks, transforms, assets, effects); stale if it differs
  layers?: {               // id-keyed map, like every other v3 map
    <layer_id>: {
      rank: string         // fractional index, jittered, tie-break on id; ascending = bottom to top
      kind: background | object | text | effect
      name?: string        // the model's label, editable
      parent_id?: layer_id // reserved for groups, null now
      asset: sha256        // RGBA PNG cropped to content; assets.origin = extracted
      mask?: sha256
      transform: { x, y, w, h, rotation? }  // signed frame pixels, not common.region: a layer may sit partly or wholly off the frame
      opacity, blend, visible, locked
      source: { op: cutout | delayer | frame_edit | generate, job_id?, model?, provider?,
                model_bbox?, model_name?, digital_source_type }
      effects?: [...]      // per-layer non-destructive adjustments (GIMP Fx, Krita filter masks)
      variants?: [{asset, job_id}], active_variant?
    }
  }
}
```

- *Undo.* Two levels, as Excalidraw and Figma do: in-session undo is an inverse-op stack over layer records (the PatchBus already returns an `inverse`), and a reorder is one `rank` patch (v3's own guard: "a reorder writes exactly one rank patch"); across sessions the frame `version`/`parent_id` chain is the durable history. Deleting a layer removes the record, never the asset.
- *Collaboration.* Records keyed by id with last-writer-wins per field, exactly the v3 rule for entities ("Entities never go into a CRDT"); no list-move operation is needed, so it works on the field-level PatchBus today and on Yjs maps or Loro later. If groups arrive, store `parent_id` and `rank` as one field so a reparent and its position update together (Figma 2019).
- *Export.* ORA is a direct serialisation (layer PNGs at 100% opacity, opacity in `stack.xml`, blend mapped to the `svg:*` set with `svg:src-over` fallback, our composite as `mergedimage.png`, a 256 px thumbnail). PSD via ag-psd: one layer per record, groups as `lsct`, composite rendered by us. C2PA 2.2 on the flattened PNG/JPEG: each AI layer is a `componentOf` ingredient placed with `c2pa.placed`, its `transform` clipped to the frame as a pixel rectangle in `changes`/`regionOfInterest`, `compositeWithTrainedAlgorithmicMedia` as the digital source type. Neither ORA nor PSD carries a manifest; it goes on the export.
- *Versioning and handoff.* A new frame version copies the layer map with changed records; assets are shared by sha256, so a version costs metadata plus new pixels. The composite stays the frame's `asset`, so Runway (which accepts flat JPEG/PNG/WebP and does not say whether alpha survives) and every existing reader are unchanged; `composed_from` tells the renderer when to re-composite before a clip job.
- *Rework risks.* Two models side by side unless `edits[]` is recast as the history of operations on layer records (the Image editor's list of numbered edits, each with its own undo, is exactly that history); a stale composite if a write path forgets `composed_from`; a `parent_id` migration later (mitigated by reserving it now); Seedream's cropped layers with bboxes and Qwen's full-canvas layers need one ingest normaliser (crop to alpha bounds, compute `transform`, keep the model's bbox and name in `source`); Seedream's `bounding_box.normalized` units are unstated (0-999 in the fal example) and must be confirmed before the normaliser is written; the `blend` enum must be the intersection of what the canvas renderer, ORA's `svg:*` set and PSD's keys support, or export is lossy. `common.region` clamps x and y to [0,1] and w and h to (0,1], so a layer dragged partly off the frame, a Seedream layer moved outside, or a future amodally completed layer that overflows would have no legal position; hence the signed pixel `transform` (or a new `layerBox` def) rather than `region`, which the generation sweep also asks for (MRT's off-canvas overflow layers and separate semi-transparent background). Note the ordering convention: the UI lists layers front first, ORA, PSD and Seedream order bottom up; `rank` ascending is bottom, the panel reverses.

**(ii) Layers as new edit kinds in `edits[]`.**

The frame stays "base image plus ordered edits"; a `delayer` edit yields layer ids and later edits (`move_layer`, `reorder_layer`, `regenerate_layer`) reference them; rendering evaluates the list.

- *Undo.* Natural: truncate or disable entries, which is how the editor's numbered edits already behave.
- *Collaboration.* An ordered list of edits that themselves reorder an ordered list: appending merges, but reordering or disabling an edit in the middle is the Yjs array-move problem, and re-running an AI step that returns a different layer count invalidates every later edit that named a layer (Figma Weave's node graph has the same property and re-runs the chain). v3 caps `edits[]` at 64.
- *Export.* PSD and ORA require materialising the layers by evaluating the list; cheap while edits are per-layer transforms, lossy once they include cross-layer blends.
- *Versioning.* Unchanged, but the composite has no record to hang its hash on.
- *Rework risks.* High. GIMP 3.0 and 3.2, Krita and Photoshop all ended with effects attached to layers and history as a separate concern; a global operation list makes layer state implicit, so the layers panel, locking, per-layer provenance and C2PA all re-derive it. Expect a migration to (i) within a few features.

**(iii) A separate layered-image document referenced by the frame.**

A new map (say `layered_images`) holds the layer stack; `frames.<id>` references it by id and version plus the composite; editing opens the sub-document (Photoshop smart object, Krita file layer, GIMP 3.2 link layer).

- *Undo.* A stack per document, familiar from smart objects.
- *Collaboration.* No new ordering problem in the frame; the frame only updates the pinned version and composite.
- *Export.* The layered document is the ORA or PSD; the frame export is flat unless we splice.
- *Versioning.* Two chains pinned together; forgetting the pin makes old frame versions re-render with new layers.
- *Rework risks.* Medium. Right if the same layered image is reused across many frames or projects (a product cut-out used in ten frames, which the existing "Save as reference" already covers for single cut-outs); otherwise navigation and a second version system for no gain. Keep as the refactor path: (i)'s layer map can be lifted into its own entity without changing the layer record.

### Recommendation

Adopt (i): a `layers` map on the frame version, keyed by id with a jittered fractional `rank`, `parent_id` reserved, per-layer `effects`, a `source` block in C2PA terms, assets with `origin: extracted`, and the composite kept as `frames.asset` with `composed_from`. Recast `edits[]` as the history of operations on those records (the editor's numbered list), not as the model. Promote a cut-out to a ref through the existing Save as reference. Normalise Seedream (cropped, bbox, name) and Qwen (full-canvas) outputs at ingest. Store variants on the layer (`variants[]`, `active_variant`), as Photoshop's generative layer does, so a regenerate does not multiply layers. The job is a `cutout` (an op the overhaul plan adds) or a new `delayer` op, which needs an `op` and a `quotaClass` value in `common.schema.json`, with `needs_input` for the async case, landing as layer records in one undo step with a decision citing the job, which is how v3 lands every other job.

UX to copy from the market: one action on an existing image, an optional plain-language hint for which elements to split, a layer count treated as a maximum (2-16), model-named layers with the background at the bottom, eye icon to hide, drag to reorder, per-layer regenerate that keeps the original hidden and grouped with the variant (Luma), disclosure of guessed pixels (IntoLayers: "hidden areas are a guess, not a recovery"), low-confidence flags on hair, glass and smoke rather than silent cuts, and OCR with a visible diff before any text is retyped (Canva's word-substitution incident; buildable now, since Claude via Bedrock is already the allowed handwriting route with TrOCR, MIT, as the fallback). Latency of 45-120 s is normal for decomposition, so the job goes through the send tray and the busy pointer, not a click; the whole-frame cut-out split goes the same way (section 3B's arithmetic: tens of seconds to a minute on WASM or iPad), and only a single click-select or Remove background is immediate. The tray lists inputs and the model, never a price or a meter; work on the device says "on your device", a fallback says "ran on our server", as the Image editor already specifies.

A yes to either is server-only and recorded in NOTICE; a no keeps the server to the written list, which still covers every model in Options 1 and 2 except PCT-Net (MPL-2.0 research code from GitHub, not a registry package), which then needs a packaged release or its own ruling.
3. **GPU budget.** Options: none (CPU tier only: Option 1 and Option 2); scale-to-zero GPU (3-10 min cold start; cents to over a dollar per image by configuration, unmeasured until the FP8 run in section 7); one warm g6.xlarge ($580 per month) or g6e.xlarge ($1,340) in working hours. This decides whether Option 3 is a 2026 feature or a 2027 one.
4. **Quality floor for shipping.** Options: ship the cut-out tier with orphan shadows and visible-fragment layers, disclosed in the UI (the floor most converters sell); or hold until fill-behind and shadow handling pass a review on the 10-frame set. The first ships in weeks; the second depends on question 3.
5. **Text.** Options: raster text layers only (what Seedream, Qwen, OpenArt and the converters return); OCR and re-set with a visible diff before anything is retyped (Canva's incident is the warning); or keep generated imagery text-free and set brand type ourselves (ties into the Brand Clan fonts). The second is buildable today: Claude via Bedrock is already an allowed provider and the handwriting route, with TrOCR (MIT, single line) as the fallback (overhaul-plan.md, the Ink row and the Handwriting row of the provider table). The third changes the generation prompts.
6. **Export at launch.** Options: ORA plus PSD (ag-psd, MIT; RGB 8-bit only, composite rendered by us, rotation baked into pixels, which is why PSD is the costlier half and sits as a conditional day in Option 1's cost), or ORA or a ZIP of PNGs only, with PSD later. PSD matters more if Adobe ships Layered Image Editing at MAX on 10-12 November 2026.
7. **Will layered images be reused across frames and projects** (a product cut-out in ten frames, a brand mark on every size)? Yes moves data model (iii) from "later refactor" to "design now" alongside Save as reference; no keeps (i) alone.
8. **Layer cap and quota class for the `delayer` op.** Charging is settled above. Open: cap layers per split at 2-16 as the market does (Seedream's maximum is 16), and give the `delayer` op its `quotaClass` (`image`, metered like a region edit, or a new per-layer class, since one split can be up to 17 billable images at the vendor). Neither changes the send tray, which lists inputs and the model only.
9. **Automatic or on demand.** Options: a \"Split into layers\" action the person runs (recommended; Canva, Luma, Seedream and the converters all work this way); the free detect-and-mask pass run by itself after every generation so the first click-select is instant, with fill and generative splits still on demand; or a full automatic split of every generated frame and picture, which multiplies the run cost by the number of images made and needs the async surfaces first.
