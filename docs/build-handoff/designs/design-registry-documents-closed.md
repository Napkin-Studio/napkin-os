## 1. Problem

The server keeps three records as ordinary CLAN documents in the tenant's tree, at `home-<tag>` ids (`crates/napkin-web/src/store.rs:52` maps any `home-*` id to `<tenant>/home-<name>.clan`, `store.rs:211` `home()`), and believes what they say. Every generic document route takes a document id from the URL, and every one of them reaches these ids: `GET /api/t/{t}/d/{doc}` mints a frame token for whoever asks (`api.rs:940`, `api.rs:154` `view`, `tokens.rs:60`), and the token's routes (`sandbox.rs:50`, every host route in `napkin-host/src/routes.rs`) write as that person with no role check. Only `home-agency-v1` is closed today, by `state::Guarded` (`crates/napkin-web/src/state.rs:412-499`, constant id plus the store's own name, fails closed).

Beside it, two leaks of budgets and costs, and one way to forge who did something on any chain.

## 3. Prior art

`state::Guarded` (`state.rs:412`): one guard on the store every route and the sandbox load through, comparing the constant id and the store's own name, failing closed (`state.rs:627` test); `Workspace::agency_store()` (`state.rs:82`) is the unguarded handle given to `napkin_host::agency` only. `brain::page::open` (`brain/page.rs:498`) refuses the registry the same way. The People store (`people.rs`) is the move-out precedent. `jobview::job_view` is the existing role-filtered shape of a job; `api.rs:597` the existing Money filter on a job's Decisions.

## 4. Approaches

**(A) One guard, a list of server-owned ids, an internal handle.** Generalise `Guarded::is_registry` to `is_server_owned`: every `home-*` id is refused for read, stamp, version, exists and apply, except the current launcher (`library::HOME_VERSION`), which is read-only (apply refused). Compare constants (`home-agency-v1`, `home-jobs-v1`, `home-clients-v1`, prefix `home-`) and the store's own `home(tag)` names, failing closed as today. Add `Workspace::registries()` returning a newtype `napkin_host::Registries<'a>(&'a dyn DocStore)` whose constructor is `pub(crate)`-hidden behind a function only napkin-web's `Workspace` calls; change `jobs::*`, `clients::*`, `agency::*` to take `&Registries` (or `&dyn DocStore` plus a registry store), and give `IndexCache::get` and `SearchCache` the registries handle beside the guarded store. The generic routes keep `ws.store` and cannot name the handle. Plus, in the same record: `update_job` replies with `job_view`; one host function `ops::read::visible(chain, money: bool)` drops `NEVER_SENT` kinds, used by `/chain`, `/decisions`, `/versions`, entry, download and export, with `money` carried on `Ctx` (a bool, wasm-clean) set by napkin-web from the person's roles; upload moves the archive's chain to `history/imported-chain.yaml` (kept, readable, read by no authority reader) and starts a fresh chain with one `upload` decision by the person, and clears `manifest.job`. Build: about 20 agent hours (guard and handle 7, cost and budget redaction 6, upload 3, client role check 1.5, tests 2.5). Run cost: none; one string compare per store call. Risks: a call site left on `ws.store` reads an empty registry (`read_registry` treats "not there" as empty) and a later write then fails 403: fails closed, no data lost, but the desk would look empty; the guard and the handle must both be right. Leaves open: the records are still CLAN files with the document machinery, and a future route given the raw handle reopens it.

**(B) Move each record into a store of its own, as people moved.** A `JobStore` and `ClientStore` trait in napkin-host (no fs, wasm-clean), a JSON file and change log per tenant in napkin-web like `people.rs`, imported once from the registry documents; the chain's `set_budget`, `set_route`, `move_deadline` become change-log lines; the job index, search, links, timesheets read the store. Build: about 45 agent hours for jobs, 12 more for clients, plus the redaction and upload pieces of A (10). Run cost: none. Risks: a data migration of every tenant's jobs and budget history; the wasm host and the desktop need an in-memory store; larger blast radius in `jobindex.rs` stamps. Leaves nothing document-shaped to open, and makes the history a server log a member cannot touch.

**(C) Keep them as documents, make them read-only to members by a role check on the generic routes.** A check in `roles::group_of` for `d/home-*` and in `sandbox::dispatch` for grants on `home-*`. Build: about 6 hours. Leaves admin and Money roles able to wipe the job list through `patch-data`, keeps every read (budgets to traffic is fine, but chain detail to admins of other concerns), must be remembered by every new route and every new token path, and does not fix the reads inside the sandbox if a token is minted elsewhere. Not recommended.

**Recommendation: A now, B for jobs as a later record if the owner wants the history out of the document format.** A closes all three records and every route at the one place every load passes through, as the agency registry was closed, in about 20 hours; B is the cleaner end state but is a migration, and A does not make B harder (the `Registries` handle is the seam B replaces).

## 8. Rollout and the data question

No infra change. The fix closes the records on first start. Tampering already done: the registries' own chains say who, because every generic data write records a decision with `actor` = the session's person, `kind: edit` and a `before` copy of what it replaced (`edit.rs:441`), while typed job writes carry `targets: [J…]`, `fields_changed: ["J…/<field>"]` and no `before`, and typed client writes record no decision at all. So on `home-jobs-v1` a decision with `before` or a bare top-level `fields_changed` is a generic write; on `home-clients-v1` any decision is. `agent` is caller-supplied and proves nothing; `actor` does. Proposed: on first start, one scan per tenant logs, per record, the count, first date and actors of generic writes, and writes one audit line for the agency's admin; nothing is reverted automatically. The `before` of the oldest generic write holds the record as it was, so an operator can restore it; later typed writes would be lost by a blind restore. Caveat: this assumes no generic route rewrites a chain (patch-data and `/edit` append; `/restore`, `/merge` and `/upstream/update` on a registry were NOT checked), and upload cannot replace an existing id. Uploaded documents already holding forged chains cannot be told apart from honest ones by their bytes; the scan can list uploads (`doc-upload-*`) whose chains carry `approve`, `sign`, `client_review`, `run_cost` or `set_budget` for an admin to look at. Roll back by redeploying the previous image (the files are unchanged in shape).
